# RENAME_AUDIT — old `www/appsflyer.js` API → `@appsflyer-sdk/js-core-plugin` (`AppsFlyerSDK`)

Temporary planning artifact for Step 4 (packaging/CHANGELOG/docs) and Step 5 (example/test-app call
sites). Not part of the shipped package. Generated by grepping every `AppsFlyer.prototype.*` in the
pre-migration `www/appsflyer.js` and comparing each against
`js-core-plugin`'s `dist/generated/methods.d.ts` / `dist/appsflyer-sdk.d.ts`.

Every old call was **callback-based** (`fn(args, successCB, errorCB)`); every new call is
**Promise-based** (`await AppsFlyer.method(params)`, single params object). That calling-convention
change applies to all ~40 rows below even where only the method/param *names* are called out —
budget Step 5's call-site rewrite accordingly, not as "mostly renames."

## Deleted, not ported (per Step 3 spec item 7 + RPC_MIGRATION_PROMPT Step 3)

- **`AppsFlyerConsent`** (constructor + deprecated `forGDPRUser`/`forNonGDPRUser` factories) — deleted. Callers build a plain object matching `SetConsentDataParams` directly (see `setConsentData` row above).
- **`AFPurchaseDetails`** — deleted per explicit instruction. Callers build a plain object matching `ValidateAndLogInAppPurchaseParams.purchase`'s `oneOf` shape directly.
- **Old `AppsFlyerError.js`** (`INVALID_ARGUMENT_ERROR`, `NO_DEVKEY_FOUND`, `APPID_NOT_VALID`, `DEVKEY_NOT_VALID`, `NO_APPID_FOUND`, `SUCCESS` string constants) — deleted. Replaced by two distinct error types with a **different error model** (no more client-side pre-validation string constants):
  - `AppsFlyerError` (from `js-core-plugin`, `code: string`) — thrown by `AppsFlyerSDK` itself.
  - `AppsFlyerRpcError` (from `cordova-transport.ts`, `code: number`) — thrown by the transport on `{success:false}`.
- **Old `MediationNetwork` global `Object.freeze({...})`** (attached directly to `window`) — deleted from `www/appsflyer.js`; re-added as a proper `MediationNetwork` TS enum in `src/constants.ts`, re-exported through the new bundle (see wire-value discrepancy below).

## MediationNetwork wire-value discrepancy — decision

This repo's pre-migration `MediationNetwork` (in the old `www/appsflyer.js`) and the
`appsflyer-capacitor-plugin` reference's `constants.ts` disagree on casing/formatting for several
entries:

| Key | This repo (kept) | Reference (capacitor) |
|---|---|---|
| `APPLOVIN_MAX` | `applovinmax` | `applovin_max` |
| `GOOGLE_ADMOB` | `googleadmob` | `google_admob` |
| `ADMOST` | `Admost` | `admost` |
| `TOPON` | `Topon` | `topon` |
| `TRADPLUS` | `Tradplus` | `tradplus` |
| `YANDEX` | `Yandex` | `yandex` |
| `UNITY` | `Unity` | `unity` |
| `TOPON_PTE` | `toponpte` | `topon_pte` |
| `CUSTOM_MEDIATION` | `customMediation` | `custom_mediation` |
| `DIRECT_MONETIZATION_NETWORK` | `directMonetizationNetwork` | `direct_monetization_network` |

**Decision: kept this repo's existing values** (left column) in `src/constants.ts`. Rationale:
these strings flow verbatim into `logAdRevenue`'s `mediationNetwork` field on the wire, and existing
integrators' dashboards/analytics config may already depend on the exact strings this plugin has
sent historically. Silently switching to the reference's snake_case values would be a silent
behavioral break for any app that (a) didn't recompile against the new enum and hardcoded the old
string, or (b) has server-side/dashboard config keyed to the old string.

**Flag for a human to verify before shipping:** the `Admost`/`Topon`/`Tradplus`/`Yandex`/`Unity`
capitalization (only these five keys — not `IRONSOURCE`, `FYBER`, `APPODEAL`, `CHARTBOOST`, which
were already all-lowercase in both this repo and the reference) looks like a pre-existing
inconsistency in this repo, not an intentional convention. If the native RPC schema's mediation
network matcher is case-sensitive and expects all-lowercase, this repo may have been silently
under-attributing ad revenue for those five networks since before this migration. This migration
does **not** fix that — it only avoids introducing a *second*, uncoordinated change to the same
values on top of an already-suspect existing one. Confirm against `af-android-plugin-bridge`'s (or
the native SDK's) actual `MediationNetworkType` string matcher before deciding whether to correct
this in a follow-up (which would itself be a breaking wire-value change requiring its own
changelog entry, separate from this migration).

## `plugin.xml` stale entry (not removed here — flagged for Step 4)

`plugin.xml`'s `<js-module src="www/AppsFlyerError.js" name="AppsFlyerError"><clobbers
target="AppsFlyerError"/></js-module>` entry now points at a deleted file
(`www/AppsFlyerError.js` was removed as part of this step). `AppsFlyerError` is a named export
inside the new `www/appsflyer.js` bundle (from `@appsflyer-sdk/js-core-plugin`), not a second
`js-module`/`clobbers` target — nothing needs a second entry. **This was intentionally left in
`plugin.xml` per this step's constraints (`DO NOT touch ... plugin.xml`)** — Step 4 must remove
that `<js-module>` block or the plugin will reference a missing file at Cordova `prepare` time.

## Consumption-shape consequence worth flagging for Step 4/5 (not a rename, but adjacent)

`plugin.xml`'s existing `<clobbers target="window.plugins.appsFlyer"/>` was written for the old
`module.exports = new AppsFlyer()` pattern, where `window.plugins.appsFlyer` **was** the SDK
instance directly (`window.plugins.appsFlyer.initSdk(...)`). The new `src/index.ts` (per this
step's mandated shape: `export * from '@appsflyer-sdk/js-core-plugin'; export * from
'./constants'; export { AppsFlyer }; export default AppsFlyer;`) bundles to a CJS module whose
`module.exports` is an **object of named exports** (`AppsFlyer`, `default`, `AppsFlyerSDK`,
`AppsFlyerError`, `AFPurchaseType`, `MediationNetwork`, …), not a reassignment to the SDK instance
itself — confirmed by inspecting the built `www/appsflyer.js` (`module.exports =
__toCommonJS(index_exports)`, not `module.exports = AppsFlyer`). That means after this migration,
callers reach the SDK via `window.plugins.appsFlyer.default.init(...)` (or `.AppsFlyer.init(...)`),
**not** `window.plugins.appsFlyer.init(...)` directly. This is a consumption-shape change on top of
every individual method rename above. Flagged here rather than silently patched with a bundler
footer hack, since the actual intended shape of `window.plugins.appsFlyer` after migration is a
packaging decision for Step 4 (which owns `plugin.xml` and the npm/CHANGELOG story), not something
to invent in this step.
